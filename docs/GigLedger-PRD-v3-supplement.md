## 1. 新定位与目标用户

### 1.1 定位怎么改

原定位是「美国自由职业者账本」：把分散收入记在一起，看清到手金额、每日底线和预留税款。

新定位改为：**一人公司（OPC）/ AI 时代独立创作者的每日成本和真实利润**。

核心卖点是 **Daily Floor（每日底线）**：把房租、保险，尤其是 ChatGPT、Claude、Cursor、API 账单这些每月固定开销，换算成「每天睁眼就要赚多少钱」。再对照实际收入，判断这个月是在赚还是在亏，以及不接新单还能撑多少天（现金跑道）。

不再把「自动报税」或「连接所有平台」当主承诺。账本是底座，Daily Floor、订阅体检和现金跑道才是用户愿意打开、愿意分享的理由。

### 1.2 目标用户

**P0（第一版只服务这群人）**

- 美国（或主要收美元、按美国自雇思路预留税款）的一人公司创始人、独立开发者、AI 应用/课程/数字产品作者、顾问
- 收入主要来自 Stripe、App Store、直接客户，以及 Upwork / PayPal 等平台
- 同时订了多份 AI 工具和云服务，固定成本不低，但很少换算成每日数字
- 自己记帐或用表格，坚持不了几周；不需要团队协作或复杂合伙架构

**明确不进入第一版**

- 网约车、外卖司机，以及需要里程/油耗/车辆模型的用户（沿用原文档 §4.2）
- 团队 / 多人协作、跨国公司、S-Corp / 多实体 / 复杂合伙人
- 以台湾或中国大陆税务规则为首要需求的用户（繁中服务谁，见第 14 节，待 Dax 决定）

### 1.3 用户故事

1. **3 分钟看到数字**：作为还没登录的访问者，我先勾选正在用的 AI 订阅、填一个大概的月收入和手头现金，马上看到 Daily Floor 和现金跑道。试算只暂存在当前页面，刷新或离开会丢失。觉得有用了，我点「用 Google 保存」完成登录，这份试算被写入我的账号。
2. **看清每天要赚多少**：作为一人公司，我把 Cursor $20/月、ChatGPT $20/月、Claude $20/月和共享办公 $900/月（100% 营业使用）加进去，系统显示 Daily Floor 约为 $29.59 + $1.97 = $31.56 / 天，我一眼知道今天至少要赚这么多。
3. **自动同步主力收入**：作为 App 和 SaaS 开发者，我授权 Stripe，并上传 App Store Connect 的 API 密钥，收入自动进账本。App Store 要分开显示「已售出」和「已到账」，因为销售报告隔天才出，财务结算大约晚一个多月。
4. **其他收入不丢**：来自 Upwork、PayPal、Fiverr 的账单我用 CSV 导入；偶尔的直接客户打款我手动记一笔。三种来源进入同一个账本，Daily Floor 和利润按总数算。
5. **订阅不重复记账**：ChatGPT 是每月自动扣费，我把它放在固定成本/订阅里，不再去支出里记一遍。只把一次性花费（例如一次设计外包、一次广告充值）记为支出。
6. **扣费前被问一句**：扣费前 3 天，系统问我「Midjourney 明天扣 $30，这个月用了吗？」。我点「常用 / 偶尔 / 没用」。连续两个月点「没用」，这项订阅标红并建议取消。系统不声称能自动检测我用没用。
7. **一键去取消**：我觉得没用时，点「管理订阅」跳到该工具的账单或取消页；点「打开产品」则跳到产品首页，提醒我去用。App Store 里买的订阅，跳到系统订阅管理页。
8. **看还能撑多久**：我输入存款 $8,000。若 Daily Floor 是 $31.56 / 天，且按「不接新单」计算，跑道约为 253 天。同时对照近 3 个月日均净收入，告诉我当前是在攒钱还是在烧钱。
9. **这个月已经落后**：本月已过 13 天，Daily Floor $29.59，累计底线是 $384.67，而本月净收入只有 $200，系统提醒「这个月已经落后 $184.67」。
10. **按项目看账，但不算 ROI**：Cursor 订阅和 Stripe 收入都打上项目标签「GigLedger」，共用订阅按比例分摊。第一版只展示该项目的收入、成本和利润，不算 ROI，也不做投放归因。
11. **自己设预留比例**：系统不再默认 15%。我看到 25%–30% 的常见参考范围，自己填 28%。预留税款按净收入 × 28% 显示，并永远带「Estimate only / Not tax advice」。
12. **导出给会计**：月度报表和 CSV 导出即可。我不必在第一版里得到季报、年报或 PDF。
13. **分享出去**：我生成「我每月的 AI 花费」或「我的 Daily Floor」卡片，发到 X 或保存后发到小红书。卡片不编造用户数或社会证明。

## 4. 计算口径（沿用原文档并补齐）

### 4.1 Daily Floor（不变）

先年化，再按天分摊：

```text
annualized_amount =
  daily × 365
  weekly × 52
  biweekly × 26
  monthly × 12
  quarterly × 4
  yearly × 1

business_annualized = annualized_amount × business_use_pct
daily_business_cost = business_annualized / 365
Daily Floor = Σ daily_business_cost   （仅统计当前日期处于生效区间内的固定成本/订阅）
```

金额计算使用高精度 decimal 或最小货币单位，不用浮点数做财务运算。界面金额四舍五入到分；验收时允许与精确值相差 $0.01。

**保留原验收示例：**

```text
$900 / 月，100% 营业使用
$900 × 12 ÷ 365 = $29.59 / 天

$900 / 月，60% 营业使用
$900 × 12 × 60% ÷ 365 = $17.75 / 天
```

营销页可以把 $29.59 展示为「约 $30」，但产品内和验收必须以 $29.59 为准，不能再把 $30 写成精确计算结果。

### 4.2 收入、本月固定成本、真实利润

```text
gross_income      = Σ income.amount          （本月，按到账日；App Store「已售出」另条展示，不默认加进本月真实利润）
platform_fees     = Σ income.platform_fee
net_income        = gross_income - platform_fees
monthly_fixed_cost = 本月各固定成本生效版本的月度分摊之和（含部分月比例分摊）
one_time_expenses = Σ 本月一次性支出的营业金额
true_profit       = net_income - monthly_fixed_cost - one_time_expenses
```

预留税款**不**从真实利润里再减一次。它是单独的储备目标。

本月真实利润默认只计入「已到账」收入。App Store「已售出但未到账」在 Dashboard 上单独一行展示，避免用户把还没入账的钱当成已经能花的利润。

### 4.3 预留税款（取代 15% 占位值）

```text
若用户未设置 tax_reserve_rate：不显示具体金额，展示「Set a reserve rate」和参考范围 25%–30%
若已设置：tax_reserve = net_income × tax_reserve_rate
```

任何税务数字旁必须同时出现：`Estimate only / Not tax advice`（繁中：`僅供預估，非稅務建議`）。

## 5. 各模块验收标准

下列全部是可测试条件。原文档 §10 的数值示例全部保留，并补充订阅、跑道、跳转等新示例。

### 5.1 Daily Floor 与固定成本

1. `$900/月、100% 营业使用`，Daily Floor 显示约 `$29.59/天`。
2. `$900/月、60% 营业使用`，Daily Floor 显示约 `$17.75/天`。
3. 同时存在 `$900/月` 共享办公（100%）+ Cursor `$20/月`（100%），Daily Floor = `$900×12÷365 + $20×12÷365` ≈ `$29.59 + $0.66 = $30.25/天`。
4. 周期换算正确：`$7/周`、100% → `$7×52÷365 = $1.00/天`；`$120/年` → `$120÷365 = $0.33/天`；`$26/两周` → `$26×26÷365 = $1.85/天`。
5. 支持周期：每天、每周、每两周、每月、每季、每年（与现有原型一致）。
6. 一项订阅从 3 月 1 日的 $20/月，改为 6 月 1 日起 $25/月：3–5 月报表仍按 $20，6 月起按 $25，3 月的历史 Daily Floor 不变。
7. 营业使用比例在 8 月 1 日从 100% 改为 60%：8 月 1 日前的历史不重算。
8. `end_date` 为 4 月 15 日的月度成本，4 月只按 15 / 当月天数分摊；5 月起为 0。
9. 订阅保存在固定成本中后，同月再记一笔同名同金额支出时，出现重复记账警告。忽略警告后仍可保存，但默认不自动双计。

### 5.2 收入、利润、手续费

1. 收入 `$120`、平台手续费 `$12`，净收入显示 `$108`。
2. 收入 `$120`、手续费选择 10%，手续费金额自动为 `$12`，净收入 `$108`。改金额或改百分比时，另一侧同步；以用户最后编辑的一侧为准。
3. 本月固定成本 `$900`，本月无一次性支出，真实利润 = 净收入 − `$900`。
4. 在上例基础上增加一次性支出 `$80`，真实利润 = 净收入 − `$900` − `$80`。
5. 预留税款和真实利润分开展示，不重复扣减。例如净收入 `$1,000`、预留比例 28% 时，真实利润仍按第 4.2 节计算；税储备显示 `$280`，利润数字不因此变成再减 $280。
6. 收入日期默认是到账日；时区按用户设置。
7. App Store 同步的一笔「已售出 $99、尚未结算」不计入本月真实利润，但在「已售出」中可见。结算进入「已到账」后，才进入利润。
8. 设置里 Apple 抽成为 15% 时，$99.99 的销售额手续费为 $15.00（四舍五入到分），净额 $84.99；改为 30% 后新同步或重算的已售出记录用 30%，已确认的历史到账记录不因这次设置改动而被改写（除非用户主动「按新比例重算未结算项」）。

### 5.3 CSV 导入

最小模板字段（表头允许英文，导入页提供可下载模板）：

| 字段 | 必填 | 说明 |

| date | 是 | 到账日，ISO `YYYY-MM-DD` |
| source | 是 | 如 `upwork` / `paypal` / `fiverr` / `other` |
| amount | 是 | 原币毛收入 |
| currency | 否 | 默认 USD |
| platform_fee | 否 | 默认 0 |
| client | 否 | |
| project | 否 | 项目标签名 |
| external_ref | 否 | 用于去重 |
| notes | 否 | |

验收：

1. 上传符合模板的 10 行 CSV，成功导入 10 笔，Dashboard 总额与文件合计一致。
2. 同一 `external_ref`（若为空，则 date + source + amount + platform_fee）再次导入，被识别为重复，不写第二笔；用户可下载「未导入行」清单。
3. 缺必填字段或金额无法解析的行不中断整批导入，失败行可下载，并告知成功/失败条数。
4. CSV 导入与导出来自同一套字段，导出后再导入不得制造重复（依赖 `external_ref` 或等价键）。
5. CSV 导入/导出是 Pro 能力。免费用户点击时进入升级说明，不得静默失败。

### 5.4 Stripe 与 App Store 同步（Pro）

**Stripe（第一个接）**

1. 用户通过 Stripe Connect 授权，或粘贴一个**只读**受限密钥（优先 Connect；若第一版用受限密钥，必须在 UI 写清风险和最小权限）。
2. 同步后，手续费和到账净额以 Stripe 返回值为准，进入同一本账，来源标记为 Stripe。
3. 同步失败（密钥无效、权限不足、超额）时展示可读错误，不写一半数据假装成功。
4. 用户可断开连接；断开后已导入的历史记录保留，不再拉取新数据。

**App Store Connect**

1. 用户提供 Issuer ID、Key ID、`.p8` 私钥。密钥**加密存储**，UI 建议使用权限最低的角色生成，并说明不要使用 Account Holder 过大权限。
2. 销售报告与财务报告分开处理：销售报告用于「已售出」（通常隔天），财务报告用于「已到账」（约晚一个多月）。
3. 两套数字同时可见，真实利润默认只算已到账。
4. 用户可撤销并删除已存密钥；撤销后无法再拉新报告。

**共同约束**

- 不做银行密码、不做页面抓取。
- 凭证不得写入前端日志、不得进入错误监控的明文 payload、不得出现在客户端源码。
- 必须保持在 Cloudflare 免费额度内（见第 12 节）。若同步频率会打满免费额度，改为「用户手动点同步」+ 每日最多一次自动同步，而不是升级付费计划。

- ChatGPT / Claude / Cursor / GitHub Copilot / Midjourney / Perplexity / Notion / Figma / Adobe Creative Cloud / X Premium
- Vercel / Cloudflare / OpenAI API / Anthropic API（API 类在第一版仍按「固定预估月费或用户填写的月度预算」记，不做用量拉取）
- 通用：域名、主机、邮箱

标价只是预填，用户可改成实际扣费金额。模板链接由我们维护；用户自定义订阅可自己填「打开产品」「管理订阅」两个 URL。为空时隐藏对应按钮，不显示空跳转。

1. 从模板一键添加「Cursor」，名称、周期（月）、参考金额预填，用户确认后进入固定成本列表，Daily Floor 立即增加 `$20×12÷365 ≈ $0.66`。
2. 该条目显示两个按钮：「打开产品」和「管理订阅」，分别跳到配置文件中的 URL（新标签页）。
3. 用户自建订阅「我的工具」，填写 `https://example.com` 和 `https://example.com/billing` 后，两个按钮跳转目标与填写值一致。

7. 某月用户改选「常用」，连续计数清零，红标取消。
8. 产品文案任何位置都不得出现「我们会自动检测你是否使用了该订阅」或等价承诺。
9. 扣费提醒是 Pro 能力（见第 11 节）。免费用户仍可手动记录订阅（最多 5 个），但没有扣费前 3 天提醒。

### 5.6 现金跑道与收入波动

设 Daily Floor = $30.25/天，存款 $8,000，近 3 个完整自然月的日均净收入为 $40：

```text
no_new_work_runway_days = floor(savings / Daily Floor)
                        = floor(8000 / 30.25) = 264 天

avg_daily_net_income_3mo = 近 3 个完整自然月净收入合计 ÷ 这些月份的日历天数之和

net_burn = Daily Floor - avg_daily_net_income_3mo
若 net_burn <= 0：显示「按近 3 个月平均收入，当前未在烧现金」，同时仍展示「若收入归零，还可撑 no_new_work_runway_days 天」
若 net_burn > 0：显示「按近 3 个月平均收入，还可撑 floor(savings / net_burn) 天」
```

若不满 3 个完整自然月，则用「已有完整月」；一个完整月都没有，则只展示「若收入归零」的保守跑道，并注明「收入平均值将在有完整自然月后计算」。

存款未填写时，跑道模块显示「添加手头现金后即可看到跑道」，不假装为 0 天。

收入波动提醒：

```text
required_to_date = Daily Floor × 本月已过天数（按用户时区，含今天）
behind_by       = required_to_date - 本月已到账净收入
若 behind_by > 0：提醒「这个月已经落后 $X」
若 behind_by <= 0：不打扰
```

验收示例：Daily Floor $29.59，日期为 11 月 13 日，本月已到账净收入 $200。

```text
required_to_date = 29.59 × 13 = $384.67
behind_by = 384.67 - 200 = $184.67
```

页面出现落后 $184.67 的提醒。若净收入改为 $400，提醒消失。

### 5.7 项目标签（不做 ROI）

1. 收入、订阅/固定成本、一次性支出都可以选一个项目标签（第一版每个条目只打一个项目，避免分摊规则爆炸）。

4. 未分摊的成本进入「未分配」，不强制用户先建项目才能记账。

### 5.8 Onboarding、持久化、语言、删除

1. 未登录访问 `/en/app`（及对应繁中路径）可在 3 分钟内走完：选至少 1 个模板或手加 1 项固定成本 → 填月收入（可填 0）→ 看到非零或明确为零的 Daily Floor，以及税/跑道模块的结果或「未设置」状态。全程不强制先登录。

3. 用户在结果页点「用 Google 保存」，完成 Google OAuth 后，当前页试算写入该账号在 D1 中的 Workspace（同一 `external_ref` 或等价键去重）。若该 Google 账号已有数据，与云端合并，之后以云端为准。登录失败或用户取消时，当前页试算必须仍在，不得先清空再报错。
4. 登录成功后再刷新或换设备，数据仍在（以 D1 为准）。已登录用户访问 `/en/app` 或官网「Sign in with Google」，直接进入其 Dashboard，而不是空白试算。
5. 未登录状态下，不得把订阅、收入、存款等写入 D1。
6. 用户在 `en` / `zh-TW` 切换后，日期、数字和货币格式正确，业务数据不变。未登录时切换语言，以不丢失当前页试算为佳；若实现上必须重载，须提前警告。
7. 删除账户经二次确认后，该用户的 Google 邮箱、姓名、收入、成本、订阅、密钥、项目、体检记录不可再被访问；再次用同一 Google 账号登录是空白工作区。

## 6. Onboarding 流程

目标：新用户不用先登录，3 分钟内在当前页面看到 Daily Floor 和现金跑道。看到数字后，用「用 Google 保存」完成登录，并把试算写入账号。

**第 0 步 — 进入**

- 营销页主 CTA「Calculate your Daily Floor in 3 minutes」进入 `/en/app`（繁中对应路径），不先弹登录墙。
- 营销页次 CTA「Sign in with Google」走 Google OAuth：未登录则登录后进入 Dashboard（无试算可合并则给空账本）；已登录则直接进 Dashboard。
- 不做单独的等候名单邮箱表单。

**第 1 步 — 你每月固定在花什么？（约 1 分钟）**

- 展示 AI/工具订阅模板，多选，可改价格。
- 可「添加其他固定成本」（租金、保险等）。
- 可跳过，但需提示：跳过后 Daily Floor 为 $0，结果意义有限。

**第 2 步 — 你大概一个月赚多少？（约 30 秒）**

- 一个数字即可，币种 USD，用于立刻出「对照 Daily Floor」的预览。
- 可选：手头现金，用于跑道。
- 预留税比例：展示「常见参考范围 25%–30%（美国自雇场景，含自雇税，仍可能不够或偏多，因联邦和州税而异）」。用户输入或暂时跳过。不预填 15%。

**第 3 步 — 你的数字（结果页，立刻出现）**

- 大数字：Daily Floor / 天。
- 对照：若第 2 步的月收入换算成每天，是高于还是低于 Daily Floor。
- 现金跑道（若已填存款）。
- 预留税款（若已设比例），带免责声明。
- 主按钮：「用 Google 保存」。完成登录后进入完整 Dashboard，当前试算已在账号里。
- 必须提示：未保存前刷新或离开本页，这次计算会丢失。不得提供「先保存在这台浏览器」或任何 `localStorage` 方案。
- 进入 Dashboard 后再引导补第一笔真实收入（手动、CSV 或同步）。

成功标准（取代原文档「先 Google 登录、5 分钟内看到数」）：

> 未登录新用户在 3 分钟内看到基于自己输入的 Daily Floor（仅暂存在当前页面）。点「用 Google 保存」完成登录后，同一份数据出现在该账号中，再刷新仍在。登录是保存和跨设备同步的手段，不是开始试算的门槛。第一版不使用 `localStorage` 做持久化。

## 7. Dashboard 信息层级

默认周期：用户时区的**本月**。顶部可切到上月。第一版不做自定义区间、不做税务季度。

从上到下，严格按此层级，避免把次要数字和 Daily Floor 抢视线：

1. **Daily Floor（主数字）**  
   每天至少要赚多少。附一句「由本月生效的固定成本/订阅换算」。
2. **本月对照**  
   - 已到账净收入  
   - 本月已过天数 × Daily Floor = 本月至今应赚  
   - 领先或落后金额（波动提醒写在这里）
3. **现金跑道**  
   保守（收入归零）和按近 3 个月平均收入两种读法，见第 5.6 节。未填存款则显示设置入口。
4. **真实利润拆解**（可用现有营销页的演示结构，但要用用户真实数据）  
   总收入 → 平台手续费 → 净收入 → 一次性支出 → 固定成本 → 真实利润。  
   App Store 若有未结算销售额，单独一行「已售出（未到账）」，不进入真实利润。
5. **预留税款**  
   仅在已设比例时出金额；永远带 Estimate only。未设置时是设置入口，不是 $0。
6. **订阅体检摘要**  
   即将扣费的项目、标红建议取消的项目。
7. **项目一览**（有项目标签才出现）  
   收入、成本、利润，无 ROI。
8. **近期明细入口**  
   收入 / 支出 / 固定成本列表，而不是把完整表格全部堆在首屏。

每周一的一句话总结固定出现在第 1 和第 2 层之间，可关闭当周展示。

## 8. 固定成本的周期、日期和比例规则

1. **周期**：每天、每周、每两周、每月、每季、每年。年化公式见第 4.1 节。
2. **开始日期**：必填，默认今天。开始日前不计入 Daily Floor 和历史利润。
3. **结束日期**：可选。结束后为 0。用于已取消的订阅。
4. **改金额、改周期、改营业使用比例、改分摊**：必须提供生效日期（默认今天，不可早于该条原始 `start_date`）。旧版本 `effective_to = 新生效日的前一天`。历史报表和历史 Daily Floor **不重算**。
5. **部分月**：`月度应计 = 该版本的年化营业额 ÷ 12 ×（本月生效天数 ÷ 本月日历天数）`。Daily Floor 只在生效日内计入该版本的日成本。
6. **营业使用比例**：0–100，整数或最多一位小数均可，但要在产品里统一一种；建议整数百分比，与当前原型一致。
7. **范围**：第一版用「营业使用比例」表达 mixed，不再单独做一个难懂的 business / personal / mixed 三选一（避免和比例重复）。比例为 0 的条目不进入 Daily Floor。
8. **订阅特有字段**：`next_billing_date`、`product_url`、`manage_url`、`template_key`、`usage_check` 记录。`next_billing_date` 在用户完成一次扣费确认或日期过后，按周期自动推到下一期。
9. **与支出的边界**：订阅/固定成本不自动生成支出记录。一次性支出不进入 Daily Floor。

## 9. 税务表达方式

第一版**不是**税务产品，只给储备目标。

必须遵守：

- 删除所有「15% planning placeholder」及其繁中「15% 規劃用預設值」。
- 不预填 15%。不把 15.3% 自雇税包装成「完整预留建议」。
- 设置文案建议使用：  
  英文：`Most US self-employed people set aside 25%–30% of net income to cover self-employment tax plus federal (and maybe state) income tax. This is a planning estimate, not tax advice. You choose the rate.`  
  繁中：`在美國自僱情境中，常見做法是按淨收入預留 25%–30%，以涵蓋自僱稅以及聯邦（和可能的州）所得稅。這只是規劃用預估，不是稅務建議。比例由你自己決定。`
- 数字旁常驻 `Estimate only / Not tax advice`。
- 不提供「已预留 / 已缴纳」对账以外的报税计算（这两项若要做，也后置；第一版可以只有比例和目标金额）。
- Tax Disclaimer 页面保留并更新：第一版是用户自设比例，不是按美国税法算出的应纳税额。
- 完整联邦所得税、自雇税、州税规则引擎全部后置。

## 10. 第一版数据模型建议

在原文档 §7 基础上增改。金额一律高精度 decimal（或整数美分）+ 原币种 + 基准币金额 + 汇率日期。禁止用 IEEE 浮点做账。

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| User | id, email, name, avatar, locale, timezone, google_sub | email、name 来自 Google 账号。未登录用户没有 User 行，试算只在当前页面内存中，不写 D1，也不写 `localStorage` |
| Workspace | id, owner_id, name, base_currency=`USD`, tax_country, tax_region, tax_reserve_rate, apple_fee_rate(15/30), cash_on_hand, cash_on_hand_as_of | 未设 rate 则为空，不是 0.15 |
| Project | id, workspace_id, name, archived | 第一版标签体系 |
| Platform / Source | id or enum: stripe, app_store, upwork, fiverr, paypal, lemon_squeezy, gumroad, paddle, direct, other | 后四个主要为手工/CSV 预留 |
| RecurringCost（含订阅） | id, workspace_id, name, category, amount, currency, cycle, start_date, end_date, business_use_pct, project_id, allocation_json, is_subscription, template_key, product_url, manage_url, next_billing_date, source | 版本化见下表 |
| RecurringCostVersion | id, recurring_cost_id, effective_from, effective_to, amount, currency, cycle, business_use_pct, allocation_json | 改金额/比例就新增版本，不改写旧行 |
| Income | id, workspace_id, source, amount, currency, base_amount, platform_fee, platform_fee_base, fee_percent, net_amount_base, date（到账日）, sale_date（可空）, recognition=`received`/`sold`, client, project_id, payout_status, external_ref, integration_id | App Store 未结算用 recognition=`sold` |
| Expense | id, workspace_id, amount, currency, base_amount, business_use_pct, business_amount_base, date, category, merchant, project_id, notes | **无 is_deductible** |
| Integration | id, workspace_id, type=`stripe`/`app_store`, status, account_label, scopes, encrypted_credentials, last_sync_at, last_error, created_at, revoked_at | `.p8` 与 Stripe 密钥只存加密后的密文 |
| UsageCheck | id, workspace_id, recurring_cost_id, period_start, period_end, billed_at, prompt_at, answer=`used`/`sometimes`/`unused`/null, answered_at | 连续两期 unused 用于标红 |
| WeeklySummary | id, workspace_id, week_start, body, shown_at | 避免重复生成 |
| ReportSnapshot | 可选；第一版也可实时汇总月度数据，不必先上独立报表表 |

约束：

- Income.external_ref 在同一 workspace 内唯一（可空，空时用应用层等价键去重）。
- Integration 凭证加密；密钥与业务数据库的访问策略要分开写在实现说明里。
- 汇率缺失时 `base_amount` 可空或为估算值，必须带 `fx_is_estimate=true`。

## 11. 免费版与 Pro 的边界

价格：**TBD**。封闭测试期间可以全部打开，但产品里要能按下面的边界关上。正式对外文案在定价验证前只写能力差异，不写死 $X/月。

## 12. 技术约束（必须写入实现计划）

- 继续托管在 Cloudflare（Pages / Workers / D1 / R2 / Cron 等）。
- **硬性约束：必须保持在 Workers Free 等免费额度内。未经 Dax 明确确认，不得升级到 Workers Paid，也不得改用任何按量计费、会自动产生账单的 Cloudflare 方案。** 这是不可谈判的发布条件。
- 若某功能（例如每小时全量同步、错误监控超量、R2 出站过大）会逼近或打满免费额度，先降频率、改成手动同步、或砍掉该实现路径，而不是升级计划。
- **第一版直接做 Google OAuth + D1。** 试算阶段的数据只在当前页面内存中，登录成功后再写入 D1。OAuth 回调 Worker 与 D1 读写都必须留在 Cloudflare 免费额度内，不得为此升级付费计划。
- 不引入 fal.ai 或其他会按调用计费的推理/API，除非 Dax 另行确认。
- 不做单独的等候名单。每周总结如需发邮件，单独列出预估用量和免费档限额，等 Dax 同意后再接。
- 不建议为了 MVP 改用自建 4C/4G 服务器。
- 产品红线沿用：不承诺银行同步、不抓取平台账号、不代用户报税、不提供投资/贷款/信用/税务建议、不编造用户数或社会证明。

## 13. 封闭测试：招募方式与反馈问题

### 13.1 招募

- 人数：10–20 人，先小后稍扩，不公开大规模获客。
- 画像：正在卖自己的产品或接美元客户的一人公司 / 独立开发者 / 创作者；最好至少用 Stripe 或 App Store 之一，并订了 2 个以上 AI 工具。
- 渠道：Dax 自己的私域和 X；如繁中要继续服务华语一人公司，再从小红书或既有中文社群补一小部分。不要混入纯本地生活服务接单者。
- 周期：至少连续使用 **14 天**（理想覆盖两个订阅扣费提醒窗口则更佳）。
- 方式：给链接 + 简短说明（这是测试版，税务只是自设比例，数据可能重置）。先让对方不登录走完 3 分钟试算，再用「用 Google 保存」把数据写入账号。第一版登录必须可用，不要发一个还不能保存的试算链接就当作测试开始。
- 成功与否先看行为，再看问卷：第 2 周是否还回来录入或同步收入；是否愿意为 Pro（同步 + 提醒 + CSV）付费及心理价位。

### 13.2 反馈问题（13 题，足够覆盖，不要再加长问卷）

使用行为：

1. 你是在登录前就看到 Daily Floor，还是卡在某一步（含「用 Google 保存」）？卡在哪？
2. 你有没有在第二天或第二周回来继续记收入？如果没有，为什么？
3. 三种收入方式（手动、CSV、同步）你实际用了哪些？哪一种最麻烦？
4. 你的订阅有没有被重复记到支出里？界面上的区分够不够清楚？
5. 扣费前 3 天的询问你有没有看到？「常用 / 偶尔 / 没用」好不好选？有没有想取消并成功跳转到取消页？
6. 现金跑道的两个读法（收入归零 / 按近 3 个月平均）你能看懂吗？哪个对你有用？
7. 「这个月已经落后 $X」有没有出现？出现时你想做什么？

价值与付费：

8. Daily Floor 这个数字有没有改变你这个月接单、砍订阅或花钱的决定？举一个例子。
9. 如果免费版只能记 5 个订阅且纯手动，Pro 才有 Stripe / App Store 同步、扣费提醒和 CSV，你会付费吗？为什么？
10. 你能接受的月费大概是多少？（开放数字，不给锚点，或测试时由 Dax 决定是否给三个选项）
11. 你还在用什么工具做这件事？（表格、QuickBooks、Keeper、手记等）GigLedger 少了什么会让你回不去旧工具，或者反过来？

信任与表达：

12. 预留税款的方式和免责声明会不会让你觉得被误导，或反过来觉得没用？
13. 你会不会把「我的 Daily Floor」或「我每月的 AI 花费」卡片发到 X / 小红书？若不会，缺什么？

结束时追加一句开放题：如果只能再做一个功能，你要哪一个？

## 15. 给 Codex 的实施顺序

按这个顺序做，完成前一项的验收再开始下一项。不要平行铺开后置功能。

1. **Google OAuth + D1 底座（必须先做）**：唯一登录方式为 Google；创建 User / Workspace；会话与回调；设置里的数据导出和立即删除。全程不超出 Cloudflare 免费额度。同一天更新 Privacy 与 Terms：说明会存储 Google 账号的邮箱和姓名，以及如何删除账户。不做 `localStorage` 持久化，不做单独等候名单。
2. **纠正当前原型的计算缺口**：去掉 15% 占位，改为用户自设比例 + 25%–30% 参考 + 免责声明；Daily Floor 精确到与 `$29.59` 示例一致。未登录试算只暂存在当前页面，并提示刷新或离开会丢失。
3. **3 分钟 Onboarding**：模板多选 → 大概月收入 / 可选存款 / 税比例 → 立即展示 Daily Floor、对照和跑道。无登录墙。结果页主按钮为「用 Google 保存」；登录成功后把当前页试算写入 D1（去重合并）；登录失败或取消时试算仍留在当前页。
4. **订阅模板 + 打开/管理链接 + 与固定成本合一的 CRUD**，含生效日期版本化、部分月分摊、禁止与支出默认双计。已登录后的增删改查写 D1。
5. **Dashboard 信息层级按第 7 节重排**；加入现金跑道、本月落后提醒、本月利润拆解。
6. **一次性支出 CRUD**（无可抵扣标记）和 **项目标签 + 分摊**（无 ROI）。
7. **CSV 模板、导入（去重、失败行下载）和月度 CSV 导出**，并按免费/Pro 边界接上开关（测试期可先全开，但开关要存在）。
8. **订阅体检**：`next_billing_date`、扣费前 3 天询问、UsageCheck、连续两月「没用」标红。第一版应用内提醒即可。
9. **分享卡片**（AI 花费、Daily Floor）和每周一应用内一句话总结。
10. **Stripe 官方同步**（Pro），再做 **App Store Connect**（密钥加密、已售出/已到账拆分、15%/30% 由用户选）。同步频率必须按免费额度设计。
11. **免费/Pro 边界落地**（5 个订阅上限、同步/CSV/提醒上锁）。价格文案保持 TBD。
12. **按第 5 节写自动化或书面验收用例**，至少覆盖原 §10 全部数值示例，以及订阅、跑道、落后提醒、跳转、「用 Google 保存」合并试算、密钥不落日志。
13. **法律页与营销页同步改到新定位**（详见《GigLedger-website-optimization.md》）：主 CTA 进计算器，次 CTA 为「Sign in with Google」，下线等候名单表单。繁中政策按第 14 节第 1 条，未决定前不扩承诺。
14. **Dax 自己当第一个用户跑两周**（必须走 Google 登录保存），再招募 10–20 人封闭测试。测试期间不做 ROI、税务引擎、银行同步、PDF、移动 App。

完成定义（可以开始封闭测试的最低标准）：步骤 1–3 必须已经可用，才能把官网主 CTA 指向计算器、次 CTA 指向 Google 登录。封闭测试最低还要步骤 4–9 可用；税务不再显示 15% 占位；用户能在未登录时 3 分钟内看到自己的 Daily Floor；点「用 Google 保存」后数据进入账号，再刷新仍在。未登录时刷新允许丢失试算，但必须有提示。步骤 10–11 应在公开宣传同步能力和开始收费前完成。
